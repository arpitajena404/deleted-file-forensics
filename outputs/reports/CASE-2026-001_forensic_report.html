7. Supported Conclusions (Evidence-Backed)

  • Historical Existence Confirmed: The file BUDGET_DRAFT.txt definitely existed on this NTFS volume, as proven by surviving Master File Table Record 38 with explicit $FILE_NAME and $STANDARD_INFORMATION structures.
  • Deletion / Unallocation Observed: The MFT record header flags byte is 0x0000 (in-use bit cleared), proving that the file entry was deallocated by the operating system file system driver.
  • Resident Data Persistence: Because BUDGET_DRAFT.txt was smaller than ~700 bytes, NTFS stored its data stream resident inside the 1024-byte MFT record itself. Deallocation unlinks the record but does not immediately zero out or overwrite resident data bytes.
  • Cryptographic Ground-Truth Match: The recovered content yielded a SHA-256 hash identical to the staged original file recorded prior to deletion. The bitstream recovery is 100% complete and authentic.

8. Limitations, Caveats, and Known Unknowns

  • Attribution Unknown: File system timestamps and MFT records prove what events occurred to the metadata and data stream, but they do not prove who sat at the keyboard, which specific user account initiated the deletion, or whether deletion was manual or automated.
  • Exact Deletion Moment Caveat: NTFS does not maintain a dedicated "Deletion Timestamp" field. The $STANDARD_INFORMATION MFT Modification timestamp ($MFT Modified) correlates closely with when the deallocation occurred, but confirmation of the exact deletion instant requires correlation with the USN Change Journal ($UsnJrnl) or Windows Security Event Logs (Event ID 4660 / 4663), which were not in scope for this isolated disk image.
  • Cluster Overwrite Vulnerability: In an active production environment, unallocated MFT records and unallocated clusters are subject to immediate reuse by subsequent write operations. Recovery was successful here because the virtual disk was detached immediately after deletion before overwrite occurred.
